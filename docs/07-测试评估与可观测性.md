# 07 · 测试、评估与可观测性

[English](../en/docs/07-testing-evaluation-and-observability.md) · [目录](../README.md)

Agent 的测试不能只断言“最后一句看起来不错”。需要同时检查确定性代码、工具轨迹、结果品质、成本、延迟和安全边界。NIST AI RMF 将测量与风险管理放在 AI 系统全生命周期中；本章将这一原则落到 Agent 工程。[NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework)

Mini Agent 的可执行入口是 [`tests/test_tutorial_agent.py`](../tests/test_tutorial_agent.py)，轨迹结构在 [`tracing.py`](../tutorial/src/mini_agent/tracing.py)。先运行全部离线检查：

```bash
python3 -m unittest discover -s tests -p 'test_*.py'
```

它不会请求模型 API。真实调用只验证厂商链路能否在那一次完成，不能替代这些固定输入的回归测试。

## 1. 四层测试

| 层 | 是否需要模型 | 例子 |
|---|---|---|
| 单元测试 | 否 | Schema 校验、权限函数、幂等键、停止条件 |
| 轨迹测试 | 可以不需要 | 用构造的 assistant/tool 消息验证分支与 ID 配对 |
| 真实调用评估 | 是 | 工具选择、参数质量、结果正确性和稳定性 |
| 端到端业务测试 | 通常是 | 在隔离环境验证真实权限、下游服务与审计 |

离线 mock 能证明控制流，不能证明厂商当前可用或模型真会选对工具。一次真实通过也不能证明所有输入稳定。这一证据边界与[模型说明书的核验规则](https://github.com/normalpeople553/HowToCallLLM/blob/main/docs/%E6%9D%A5%E6%BA%90%E4%B8%8E%E6%A0%B8%E9%AA%8C%E8%A7%84%E5%88%99.md)一致。

## 2. 评估集不只有“正常问题”

每条样本应包含输入、必要前置状态、期望的工具/禁止的工具、结果约束和风险标签。数据集至少覆盖：正常请求、模糊请求、超出能力、工具失败、无权访问、提示注入、超长输入、重复请求和需要人工确认的动作。

评估器可以是确定性规则、人工标注或模型评分。优先用确定性规则检查工具名、参数、权限、引用和状态；模型评分用于难以编码的品质判断，并使用人工样本校准。[OpenAI Graders 作为一种官方实现参考](https://platform.openai.com/docs/api-reference/graders)

## 3. 轨迹比最终文本更能解释失败

每个任务建议有 `trace_id`，每个模型请求和工具调用有独立 span。记录模型和版本、提示或配置版本、轮次、工具名、延迟、结束原因、token/费用、错误类型与安全决策。不要默认记录密钥、完整用户文本、工具敏感回包或隐藏思考内容。

先定义一套安定的错误分类，再做仪表盘；否则所有失败都会变成不可操作的“Agent 失败”。

## 4. 上线门禁

项目建议每次改动模型、提示、工具 Schema、路由、记忆或检索策略时，重跑相关切片和固定回归集。只有在核心成功率、高风险误动作率、成本和 P95 延迟都满足业务阈值时才放量。阈值由业务自定，不存在一个通用满分。

## 检查表

- [ ] 单元、轨迹、真实调用和端到端测试的证据分开记录；
- [ ] 评估集包含失败、攻击和无权场景；
- [ ] 工具轨迹、最终结果、成本和延迟都有指标；
- [ ] 日志脱敏并有保留期；
- [ ] 变更后重跑对应回归集；
- [ ] 上线阈值与业务风险相匹配。
