# 03 · 多工具、路由与循环控制

[English](../en/docs/03-multiple-tools-routing-and-loops.md) · [目录](../README.md)

一个工具可以用 `if`处理，多个工具则需要明确的注册表、路由器、执行器和循环预算。厂商工具字段、并行调用和 `tool_choice` 能力必须按准确型号核对。[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/) · [模型说明书工具示例](https://github.com/normalpeople553/HowToCallLLM/blob/main/models/deepseek/deepseek-flash/examples/05_tool_calling.py)

## 1. 四个组件

| 组件 | 职责 | 不应负责 |
|---|---|---|
| 工具注册表 | 名称、描述、Schema、风险等级、处理函数 | 让模型动态注册任意函数 |
| 路由器 | 将允许的工具名映射到本地处理器 | 用 `eval` 执行模型文本 |
| 执行器 | 校验、授权、超时、执行和标准化结果 | 让工具绕过业务权限 |
| 循环控制器 | 保存消息、追踪 ID、控制轮数与停止 | 无限 `while True` |

模型返回工具名和参数，但映射到哪个真实函数由应用决定。这一边界也是第一章可执行示例的核心。

## 2. 工具描述就是路由界面

项目建议让工具名表达一个稳定动作，描述说清“什么时候用”与“什么时候不要用”，参数只放执行所需的最小数据。两个高度重叠的工具会增加路由歧义；先合并职责，再用明确的枚举参数区分子动作。

工具列表不是权限列表。即使某个工具已展示给模型，每次真正执行时仍应按用户和资源重新授权。这是本项目的安全建议，与 [OWASP Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) 的最小功能、最小权限和降低自主性原则一致。

## 3. 一个可控的循环

下面是控制流伪代码，不是某个厂商的调用示例：

```text
设置 max_turns、max_tool_calls、deadline 和 cost_budget
重复：
  如任一预算超限：停止并报错
  请求模型
  如果是最终正文：检查结束原因后返回
  如果是工具调用：
    先校验整批调用
    根据依赖和副作用决定串行或并行
    执行并保存每个 tool_call_id 的结果
    继续
  其他响应：停止并报错
```

不应因为一批调用在同一次响应里就自动并行。读操作且互不依赖时才适合并行；有顺序依赖、共享锁或副作用时应串行。这是项目级调度策略，不是模型协议自动保证。

## 4. 幂等与重试

只有在能判定前一次未造成副作用，或下游支持幂等键时，才可自动重试写操作。项目建议用稳定的业务请求 ID 做去重，将“已接收”、“已执行”和“结果已返回”分开记录。模型说“成功”不是业务成功证据。

## 5. 停止原因

Agent 至少要区分：正常完成、用户取消、需要追问、等待确认、参数错误、工具错误、超时、超轮数、超成本和安全拦截。对用户的回复与内部机器状态分开，才能在测试和监控中统计真正失败原因。

## 检查表

- [ ] 工具名只能映射到静态白名单；
- [ ] 整批参数先校验，再执行任何一个工具；
- [ ] 轮数、工具数、时间和费用都有上限；
- [ ] 副作用重试有幂等或去重保护；
- [ ] 并行只用于无依赖、可并发的调用；
- [ ] 停止原因可机器读取并可监控。
