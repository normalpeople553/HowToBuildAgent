# 04 · 会话状态、短期记忆与上下文管理

[English](../en/docs/04-state-memory-and-context.md) · [目录](../README.md)

“记住”不是一个单一功能。本章把它拆成模型上下文、会话状态、业务状态和长期记忆四层。这是本项目的工程分类，不是厂商通用标准。

## 1. 四层数据

| 层 | 典型内容 | 真实性要求 | 建议存储 |
|---|---|---|---|
| 模型上下文 | system/user/assistant/tool 消息 | 可裁剪，但工具协议必须完整 | 每次请求组装 |
| 会话状态 | 当前步骤、待确认操作、临时偏好 | 有明确会话边界 | 会话库或缓存 |
| 业务状态 | 订单、付款、权限、任务状态 | 必须以业务系统为准 | 业务数据库 |
| 长期记忆 | 经授权保留的稳定偏好或事实 | 可查看、修改、删除和过期 | 独立记忆存储 |

`messages` 是发给模型的当次上下文，不应代替业务数据库。模型生成的总结是派生数据，不能覆盖原始业务记录。

## 2. 每轮现组上下文

项目建议的组装顺序：

```text
系统规则与安全边界
  + 当前用户和会话的最小必需状态
  + 与当前任务相关的历史摘要
  + 必须保留的完整工具调用链
  + 当前用户输入
```

不要默认将整个数据库、所有聊天历史或完整工具回包发给模型。这会增加成本、超出上下文限制，也可能扩大敏感信息暴露面。准确的上下文长度与输出预算查[模型说明书](https://github.com/normalpeople553/HowToCallLLM/tree/main/models)的准确型号页。

## 3. 摘要不是原始记录

对较早历史做摘要时，保留可追溯的原始消息 ID，将摘要版本、生成方法和时间与正文分开。权限、金额、订单状态等关键事实应从真实系统重新读取，不从模型摘要恢复。

工具链不能随意压缩：模型请求的工具调用、对应 `tool_call_id` 和工具结果必须保持配对。某些思考模式还要求回传特定字段，以准确型号的官方文档为准。[DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)

## 4. 长期记忆的写入门槛

不要把每句聊天都写成长期记忆。项目建议只保留：用户明确要求保留的信息、对后续任务有稳定价值的偏好，以及有业务依据的持久事实。每条记忆至少带用户/租户、来源、类型、有效期和删除机制。

模型从用户语句推测出的属性应标为推断，不与用户明确陈述或业务事实混在一起。

## 5. 并发与隔离

每个会话更新应带版本号或原子条件，防止两个并发 Agent 轮次相互覆盖。所有查询必须带用户/租户边界，不靠提示词要求模型“不要读别人数据”。权限隔离必须在存储和工具层强制。

## 检查表

- [ ] 模型上下文、会话状态、业务状态和长期记忆分开存储；
- [ ] 关键业务事实从真实系统读取，不信任历史摘要；
- [ ] 工具调用与结果 ID 完整配对；
- [ ] 长期记忆有来源、有效期、删除和用户隔离；
- [ ] 并发更新有冲突检测；
- [ ] 发给模型前做数据最小化和敏感信息检查。
